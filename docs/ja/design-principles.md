# Design Principles — North Star 6 原則

Umlay のあらゆる設計判断は、次の 6 原則をこの順序で参照して下します。トレードオフが発生した場合は、番号の小さい方を優先します。

> 「UML 図のコンセプトは継承するが、レガシー言語 (Java 中心の DDD) には寄せない」が通奏低音です。関数・イミュータブル・async・分散を第一級で扱います。

## 1. AI 生成結果が目的に合うか

**意味**: モデルを AI に渡したときに、狙い通りのコード / DDL / 設定が出ること。

**成功指標**: ゴールデンテスト合格率 ≥ 90%。

**影響**: DSL / IR には、生成コードの骨格を決めるのに足る情報 (型 / 不変条件 / 意図) を載せる。レンダリング目的だけの表層情報は避ける。

## 2. Node / クラウドに適用可能か

**意味**: 関数コンポーネント、Lambda、Queue、Worker、KV ストアが**一級市民**。クラス継承前提のレガシー DDD には寄らない。

**成功指標**: 代表スタック (Next.js + Prisma + AWS など) で E2E 生成が通る。

**影響**: 予約語に `function` / `queue` / `component` / `worker` / `kv` 等を持つ。`@service` は関数集約としても表現可能。

## 3. レビューが「回る」か

**意味**: 見つけやすい → 修正しやすい → モデルに反映しやすい、の循環。

**成功指標**: 指摘 → 修正 → マージの中央値 < 10 分。

**影響**: DSL はテキスト・Git 親和。レビュー注釈 (`@review` / `@fix`) は属性単位。Stable ID により rename 耐性を持つ。

## 4. AI が設計リスクを能動的に指摘

**意味**: 「マルチスレッド化の考慮漏れ」「ref 依存の過剰再レンダリング」など、**聞かれる前に**先回りする。

**成功指標**: リスクカタログのヒット率を測定。

**影響**: Lint / スコアにとどまらず、アンチパターン検出ヒューリスティックと AI レビューを両建て。IR に `data-risk` を乗せるフック点を持つ。

## 5. 出力図が CSS で拡張可能

**意味**: 色 / サイズ / フォント / レイアウトをユーザー資産として持込・配布できる。

**成功指標**: テーマ適用が 1 ファイルで完結する。

**影響**: SVG は CSS 変数 (`--uml-*`) + セマンティッククラス (`uml-*`) で構造化。テーマは外部 CSS で差し替え可能。

## 6. 画像を資料として挿入可能

**意味**: ワイヤフレーム、ホワイトボード写真などを**補足ドキュメント**として添付できる。ただし**構造情報は汚さない**。

**成功指標**: 添付画像を変更してもモデル IR は変わらない。

**影響**: `@@attachments(...)` ブロックは別管理され、図本体には埋め込まれない。

---

## レガシー UML からの脱却 (声明)

以下は Umlay が**暗黙に要求しない**ものです。従来の UML ツールがこれらを前提に設計されてきたこととは距離を置きます。

- 継承階層主義 (is-a での構造表現を強要しない)
- getter / setter 前提 (プロパティアクセスは表層問題と扱う)
- 同期一択 (async / message passing を第一級で)
- 単一プロセス前提 (分散 / イベント駆動を扱える)

## 非目標 (Non-Goals)

| 目標 | 扱わない理由 |
| --- | --- |
| マウスドラッグ中心のビジュアル編集 | Lucidchart / draw.io の代替は狙わない |
| BPMN / SysML フルサポート | 初期は UML + ER + スケジュール系に集中 |
| OS レベルの図 (配置図) | 後続フェーズ |
